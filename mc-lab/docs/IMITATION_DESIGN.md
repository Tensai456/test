## 0. หลักคิด 5 ข้อ (อ่านก่อน)

1. **รุ่นพี่คือ "โค้ช" ไม่ใช่ "เฉลย"** — สมองเดิมตาย 704 ครั้ง/166 ชม. (4.2 ครั้ง/ชม.), ยืน AFK, ขุดมือเปล่า, ไม่กินตอนเลือดต่ำ (brief §1). ดังนั้น "เหมือนรุ่นพี่" ไม่ใช่เป้า — เป้าคือ "เหมือนตอนรุ่นพี่ทำถูก และต่างตอนรุ่นพี่ทำผิด"
2. **reflex/veto ของ `decide()` เป็น hard constraint ตลอด** — ข้อมูลจากรุ่นพี่ปรับได้แค่ threshold, เพิ่มกฎ, หรือจัดอันดับ "แผน" (plan) ภายใต้เพดานความปลอดภัย ห้ามเอาข้อมูลมาปลด veto
3. **ปรับครั้งเดียว** (ตามเป้าใหญ่ใน brief): แบ่งข้อมูลเป็น train/holdout ก่อนมองผล · ห้ามวนปรับจนเข้าหา holdout (ดู §8)
4. **จุดที่ข้อมูลช่วยได้จริง** คือ (ก) threshold ที่ตั้งด้วยสัญชาตญาณ (เช่น `hungry: foodBelow 7`, `eat-to-regen: hpBelow 11 / foodBelow 18`), (ข) สถานการณ์ที่ยังไม่มีกฎ, (ค) ลำดับ/เวลาของ chain (`data/chains.json`), (ง) ตัดสิน "แย้งถูก/ผิด"
5. **โมเดลเล็กเป็นทางเลือก ไม่ใช่ทางหลัก** — กฎ+ตารางตัดสินใจอ่านเข้าใจได้ fuzz ได้ (fuzz ผ่านเฉพาะ `decide()` ไม่ใช่โมเดล) · ถ้าใช้โมเดล ต้องอยู่ใต้ `decide()` เสมอ (§5.4)

## 1. ข้อมูลที่จะได้ (jsonl ทุก ~250 ms = 4 แถว/วินาที/ตัว)

ไฟล์แยกตามบทบาท (จะวางไฟล์ไว้ที่ `logs/s39/` [คิดเอง — โฟลเดอร์ยังไม่มีในแล็บ ให้ jing ยืนยัน]):

| ไฟล์ | ผู้เขียน | หนึ่งแถวคือ |
|---|---|---|
| `senior_<ชื่อ>.jsonl` | ตัวบันทึกฝั่งรุ่นพี่ (Jarvis/Fable/Nexus/Vikta) | สถานะตัวเอง + ท่าที่ทำ + "ความคิด" ของสมองเดิม |
| `intern_<ชื่อ>.jsonl` | ผู้ฝึกงาน Sonar27–30 | สิ่งที่โซนาร์เห็น + ความคิดเงา + การแย้ง + คำตัดสิน |

### 1.1 สคีมาแถวรุ่นพี่ (เสนอ)
```jsonc
{ "t": 123456789,          // ms เวลาเครื่อง (ไว้ซิงก์) 
  "tick": 5832100,         // bot.time.age ถ้ามี (ใช้แทนนาฬิกา — เซิร์ฟแล็กแล้วเพี้ยน; mineflayer_state ก็ใช้ age*50)
  "who": "Jarvis",
  "pos": [x,y,z], "yaw": 0.0, "pitch": 0.0, "vel": [vx,vy,vz], "onGround": true,
  "hand": "iron_sword", "offhand": "shield", "armor": ["iron_helmet",null,"iron_leggings","iron_boots"],
  "inv": {"oak_log": 12, "cooked_beef": 5},
  "hp": 17.0, "food": 14, "air": 20, "dim": "overworld", "pose": "standing|sneaking|swimming|gliding|sleeping",
  "act": {"dig": "stone", "place": null, "attack": "zombie#123", "use": "eat|shield|bow|null", "key": ["forward","sprint"]},
  "effects": ["speed"], "timeOfDay": 13000,
  "oldBrain": {"goal": "...", "thought": "...", "action": "..."},   // ข้อความจากสมองเดิม (qwen3:8b + กฎ)
  "events": ["hurt:3.0:zombie","death","spawn","chat:..."] }          // ตั้งแต่แถวก่อนหน้า
```
### 1.2 สคีมาแถวผู้ฝึกงาน
```jsonc
{ "t":..., "tick":..., "who":"Sonar29", "watching":"Fable",
  "sonar": {"nearby":[{"type":"zombie","dist":3.2,"hostile":true}], "blocks":[...]},   // รูปแบบเดียวกับ state.nearby / state.nearBlocks
  "seniorSeen": {"pos":[..],"hand":"..","armor":[..],"pose":"..","hp":null},            // เท่าที่ "ตา" เห็นได้ ไม่มี inv/food (ดู §1.3)
  "shadow": {"kind":"rules|fly-small|smart|fly-full","decision":{"mode":"reflex","rule":"hungry"}, "thought":"..."},
  "objection": {"id":"o-0412","rule":"dig-straight-down","claim":"รุ่นพี่ขุดลงตรง","evidence":{...},"at":123456}, // null ถ้าไม่แย้ง
  "verdict": {"objId":"o-0412","result":"right|wrong|unknown","by":"auto|human","after_s":10,"basis":"hp -6 / lava"} }
```
### 1.3 ข้อจำกัดที่ต้องรู้ตั้งแต่ตอนวาง logger
- ผู้ฝึกงานเห็นรุ่นพี่ผ่านโปรโตคอลเท่านั้น: ตำแหน่ง/มอง/ท่าทาง/ของในมือ-เกราะ **น่าจะ** ได้จาก entity equipment/metadata [ไม่แน่ใจ — ต้องเช็กกับ mineflayer 4.39 + ViaVersion 26.1] แต่ **ไม่เห็น inv/food ของคนอื่น** (hp ของคนอื่นผ่าน metadata ได้บางกรณี [ไม่แน่ใจ])
- ดังนั้น "state ที่ครบเพื่อป้อน decide()" ของรุ่นพี่ ต้องมาจาก logger **ฝั่งรุ่นพี่เอง** เท่านั้น · ถ้า logger ฝั่งรุ่นพี่ใส่ไม่ทัน (สมองเดิมเป็นสปาเก็ตตี้) → fallback = ผู้ฝึกงานเห็นได้แค่ชุดย่อย → ใช้กับกฎที่ไม่ต้องพึ่ง inv/food ได้เท่านั้น (ดู §3 คอลัมน์ "แหล่ง")
- **ขนาดข้อมูล** (คำนวณเอง จากสมมติว่า log ต่อเนื่อง): 4 แถว/วิ × 3600 = 14,400 แถว/ชม./ตัว · × 4 ตัว × 72 ชม. ≈ 4.15 ล้านแถว เป็นเพดานบน (จริงน้อยกว่าถ้าตาย/ออฟไลน์/ไม่ log ตอนอยู่นิ่ง) [คิดเอง ว่า 3 วัน = 72 ชม.]
- ทำ `idle compression`: แถวที่ตำแหน่ง/กระเป๋า/hp ไม่เปลี่ยนติดกัน เก็บเฉพาะแถวแรก+ความยาว (ลดไฟล์ได้มาก) แต่ **อย่าทิ้งเมตาว่าอยู่นิ่งกี่วิ** เพราะ `idle`/AFK คือ negative label (§6)

## 2. ภาพรวม pipeline

```
jsonl (รุ่นพี่+ผู้ฝึกงาน)
  → [A] ตรวจคุณภาพ/ซิงก์ (เวลา, แถวหาย, tick กระโดด)
  → [B] rowToState()  (ตาราง §3)  ──►  state ตามสัญญาของ decide()
  → [C] replay: decide(state, goal) ──► predicted {mode, rule.id | step.id, vetoes[]}
  → [D] actionClass(row, window)   ──► actual  {eat, flee, fight, mine, place, sleep, idle, ...}
  → [E] diff + ติดป้ายผลลัพธ์ (ตาย/เลือดลด/AFK) ──► ตาราง agreement / รายกฎ / รายแย้ง
  → [F] ผลิตข้อเสนอ: (a) แก้ triggers.json  (b) ตารางตัดสินใจ  (c) ชุดฝึกโมเดล
  → [G] ประตูตรวจ: unit test + fuzz ซ้ำ + holdout  → จึงปล่อย
```

## 4. Replay harness (ป้อน state ที่ log ไว้เข้า `decide()` แล้ว diff กับท่ารุ่นพี่)

### 4.1 โครงไฟล์ที่เสนอ (แยกตามหน้าที่ ≲300 บรรทัด/ไฟล์ ตามกติกา brief) — ยังไม่ได้เขียนโค้ด
```
tools/replay/
  load_jsonl.mjs     // อ่านเป็นสตรีม + ตรวจ tick กระโดด/ซ้ำ (ไม่โหลดทั้งไฟล์เข้าหน่วยความจำ)
  row_to_state.mjs   // ตาราง §3 + tracker ข้ามแถว (fallDistance, idle, provoked) + _missing
  action_class.mjs   // jsonl → คลาสท่า (eat/flee/fight/mine/place/sleep/idle/…)
  rule_expect.mjs    // ตาราง: rule.id → คลาสท่าที่ "ควรเห็น" ภายใน T วินาที
  replay.mjs         // วนแถว: decide() → เทียบ → เขียนผล .jsonl + สรุป
  metrics.mjs        // agreement / precision / recall / objection accuracy
  outcome_label.mjs  // ติดป้ายผลลัพธ์ (ตาย/เลือดลด/AFK) เพื่อแยก "รุ่นพี่ทำดี/ทำแย่"
test/replay.test.mjs // node:test: ป้อนแถวสังเคราะห์ → ตรวจ state + ผล diff
```
- ใช้ `decide` ที่ import จาก `lib/chain.mjs` **ตัวเดียวกับที่ใช้จริง** (ไม่ก๊อปปี้) เพื่อให้ replay ตรงกับบอตจริง
- **อย่า** เรียก `toState(bot)` (ต้องมี bot จริง) — เขียน `rowToState` แยก แล้วเขียน test เทียบกับ `toState` โดยสร้าง fake bot จาก fixture เดียวกันให้สองทางได้ state เท่ากัน (กัน drift)

### 4.2 อัลกอริทึมต่อหนึ่งแถว
1. `s = rowToState(row, tracker)` ; `d = decide(s, goal)`
2. `pred = d.mode==='reflex' ? {kind:'reflex', id:d.rule.id, veto:!!d.rule.veto} : d.mode==='plan' ? {kind:'plan', id:d.step.id} : {kind:'done'}` + `d.vetoes[].id`
3. ท่าจริง: `act = actionClass(rows[i .. i+W])` โดยหน้าต่าง W [คิดเอง: ตั้งต่อกฎ ไม่ใช่ค่าเดียว เช่น กินภายใน 2–5 วิ, หนีครีปเปอร์ภายใน 1 วิ — ปรับจากข้อมูล ไม่ใช่เดา]
4. ตัดสินผลเทียบ:
   - **match** : `act ∈ rule_expect[pred.id]`
   - **miss** : มี reflex ทำนาย แต่รุ่นพี่ทำอย่างอื่น
   - **extra** : รุ่นพี่ทำท่าป้องกัน (เช่น กิน/หนี) แต่ `decide` ไม่ยิง reflex ใด
   - **veto-breach** : `act` ตรงกับท่าที่ veto ห้าม (เช่น ขุดลงตรง, นอนนอก overworld) → **ไม่นับเป็น disagree ของเรา** แต่เป็นผู้สมัคร "รุ่นพี่ผิด" (ลิงก์ไปคำแย้ง §4.4)
5. เขียนผลแถวละหนึ่งบรรทัด: `{t, who, pred, actual, class:"match|miss|extra|veto-breach|unknown", missing:[...], outcome:{...}}`
6. ตอนจบรายงาน: ตารางต่อกฎ + ต่อรุ่นพี่ + ต่อ "วันในเกม" (เพื่อดูว่าตกตรงช่วงไหน)

### 4.3 กติกาตัวส่วน (กันตัวเลขหลอก)
- `unknown` (ประเมินไม่ได้เพราะ `_missing` ครอบคลุมคีย์ที่กฎใช้) **ไม่ถูกนับในตัวส่วน** แต่ต้องรายงานจำนวนแยกเสมอ ("agreement 92% บนแถวที่ประเมินได้ 40% ของทั้งหมด" ต้องเขียนทั้งคู่)
- ตัดแถวช่วง `respawnGrace`/`justDied` ออกจาก agreement ปกติ (รายงานแยก) เพราะเป็นช่วงที่สมองเราสั่งห้ามวางบล็อก
- ตัดแถวที่ `chunkUnloaded` / ping หรือ tps เสี่ยง (ถ้ามี) ออกเช่นกัน

### 4.4 การจับคู่คำแย้ง
- แถวแย้ง (`objection`) ของผู้ฝึกงานผูกกับ id กฎ → replay ตรวจว่า `decide()` ณ ขณะแย้ง **ยืนยันกฎเดียวกันหรือไม่** (ผู้ฝึกงาน 27 ใช้กฎล้วน ควรตรง 100% โดยโครงสร้าง ถ้าไม่ตรง = บั๊ก pipeline ไม่ใช่ข้อมูล → ใช้เป็น sanity check ฟรี)

## 5. สามทางที่ข้อมูลเปลี่ยนเป็นความสามารถ

### 5.a อัปเดตกฎใน `data/triggers.json`

| ประเภท | ตัวอย่าง (อ้างกฎที่มีในไฟล์จริง) | ข้อมูลที่ใช้ตัดสิน | เกณฑ์ผ่าน [คิดเอง] |
|---|---|---|---|
| **ปรับ threshold** | `hungry` (`foodBelow:7`), `eat-to-regen` (`hpBelow:11`,`foodBelow:18`), `outnumbered` (`atLeast:4`,`hpBelow:14`), `idle` (`idleSecondsOver:30`), `hostile-close` (`within:4`) | กระจายค่า food/hp ตอนรุ่นพี่ "กินเมื่อรอด" เทียบ "กินตอนตาย" · ตัดที่ค่าที่ลด death-within-60s โดยไม่ทำให้ rule ยิงถี่เกิน | ต้องมี ≥ N เหตุการณ์ต่อ bin (N = [คิดเอง] 30) ไม่งั้นไม่ปรับ |
| **ปรับ prio** | ลำดับ reflex ที่ชนกันบ่อย (ดูตาราง "also" ใน `decide()`) | คู่กฎที่ยิงพร้อมกัน แล้วรุ่นพี่เลือกอันที่ไม่ใช่ prio สูงสุด **และผลดี** | ห้ามลด prio ของ veto หรือกฎ ≥ `REFLEX_MIN`(50) ด้านเอาตัวรอดโดยไม่มี fuzz ใหม่ |
| **กฎใหม่** | สถานการณ์ที่รุ่นพี่ตาย/เลือดหมดโดย `decide()` ไม่ยิง reflex ใดใน 10 วิ ก่อนเหตุการณ์ (หา "ช่องว่างการตาย") | คลัสเตอร์ของ state ก่อนตาย (clusterable ด้วยการจัดกลุ่มตามเงื่อนไขหลัก) | ต้องอธิบายเป็นเงื่อนไข `test()` ที่มีอยู่ได้ — ถ้าต้องมี key ใหม่ ต้องเพิ่มใน `test()` + เทส |
| **ปิด/ลดกฎ** | กฎที่ precision ต่ำ (ยิงบ่อยแต่รุ่นพี่ที่รอดไม่ทำตาม) | per-rule precision บนแถว outcome ดี | ห้ามปิดกฎ veto/ความปลอดภัยด้วยเหตุผล precision (เพราะ "รุ่นพี่ไม่ทำตาม" ≠ "กฎผิด") — ต้องมี outcome ดีรองรับ |
| **ปรับ chain** | ลำดับ/เงื่อนไข `done` ใน `data/chains.json` (first_night 7 ขั้น, iron_kit 8, nether 6, end 6, dragon 4, home_keep 5, farm 4) | เวลาจริงที่รุ่นพี่ใช้ต่อขั้น vs ตาราง "วันต่อวัน" · ขั้นที่รุ่นพี่ข้ามแล้วรอด | เทียบกับ SURVIVAL_DAYBYDAY ก่อน (ถ้าไฟล์นั้นมี) ไม่แก้ chain จากข้อมูลล้วน |

**ขั้นตอนบังคับทุกการแก้กฎ:** แก้ใน branch/สำเนาไฟล์ → `node --test` → fuzz ซ้ำ (อย่างน้อยตามกติกา EVENT_INVENTORY: เหตุการณ์ละ ≥2,000,000; เจอช่องโหว่ → ปิดแล้วรันต่อ) → จึง merge · ห้ามแก้ `data/triggers.json` สดระหว่างเซิร์ฟเล่นอยู่

### 5.b ตารางตัดสินใจ (decision tables)
ใช้เมื่อพฤติกรรมเป็น "เลือกค่า" ไม่ใช่ "ตรวจเงื่อนไขอันตราย" — ตัวอย่าง:
- **เลือกอาหาร/เวลากิน**: ตาราง (hp bin × food bin × มีศัตรูไหม) → กินเมื่อไหร่ที่รุ่นพี่รอดบ่อยสุด
- **เลือกอาวุธ/โล่ต่อชนิดม็อบ** (เชื่อม `lib/pvp`, `bestWeapon`): ตาราง (ม็อบ × อาวุธในมือ) → อัตราลดเลือดต่อวินาทีเฉลี่ย
- **เวลาเปลี่ยนกิจกรรมตามวัน/เวลา**: ตาราง (วันในเกม × ช่วงเวลา × goal) → ขั้น chain ที่รุ่นพี่ทำอยู่
- **ขนาด bin ต้องคุมให้ n ต่อเซลล์พอ**: เซลล์ที่ n < [คิดเอง] 30 → ใช้ค่าเดิมของกฎ ไม่ใช้ค่าจากข้อมูล
- เก็บเป็น JSON ในไฟล์ใหม่ (เช่น `data/decision_tables.json` [ข้อเสนอ — ไม่แตะ data/ ตอนนี้]) และโหลดโดยฟังก์ชันล้วนที่เทสได้

### 5.c โมเดลเล็ก (ทางเลือก) — เทรนบน RTX 3060/4060
**บทบาท:** ช่วยเลือก "แผน/ท่าย่อย" ในโหมด `plan` (ใต้ `REFLEX_MIN`) และเป็นตัวให้คะแนน "น่าจะแย้ง" — **ห้ามแทน reflex/veto**
- **ฟีเจอร์ (input)** = เวกเตอร์จาก state ใน §3 ที่ทำให้เป็นตัวเลข: hp, food, air, fallDistance, idleSeconds, time (sin/cos วัน), dim (one-hot), pose, ระยะ/จำนวนม็อบแต่ละหมวด (hostile ใน 4/6/16, provoked, armored), ข้อมูลเครื่องมือ (tier ของของในมือ), จำนวนของสำคัญใน inv (ไม้/หิน/เหล็ก/อาหาร/ถ่าน ฯลฯ), เกราะครบกี่ชิ้น, flags หลัก, one-hot ของ `step.id` ปัจจุบันจาก `nextStep()` · ประมาณ 100–200 มิติ [คิดเอง] 
- **ฉลาก (label)**:
  1. weak label = เอาต์พุต `decide()` (rule.id / step.id) — ใช้ pre-train ให้โมเดล "เท่ากับสมองใหม่" ก่อน (ไม่ได้ความรู้ใหม่)
  2. strong label = `actionClass` ของรุ่นพี่ **เฉพาะแถวที่ outcome ดี** (ดู §6) — ส่วนนี้คือความรู้ใหม่
  3. ถ้า 1 ≠ 2 บนแถวที่ outcome ดีซ้ำ ๆ → ตัวอย่าง "ที่กฎควรเรียนรู้" (ส่งไปหัวข้อ 5.a ด้วย ไม่ปล่อยแค่ในโมเดล)
- **ขนาด** [คิดเอง]: MLP 2 ชั้นซ่อน 128 หน่วย × เอาต์พุตตามจำนวนคลาสท่า (~20–40) ≈ หลักหมื่นพารามิเตอร์ (คำนวณ: 150×128 + 128×128 + 128×40 ≈ 40,800) หรือ gradient-boosted trees ถ้า tabular · เล็กพอที่ **CPU เทรนได้** — RTX 3060/4060 ไม่ใช่คอขวด (ค่า VRAM ของการ์ดไม่ใช่ปัจจัยที่ต้องกังวลกับโมเดลขนาดนี้) · ไม่ต้องใช้ GPU กับโมเดล tabular ขนาดนี้
- **การ inference ในบอต:** รันนอก event loop ของบอตหรือด้วย ONNX/ตาราง lookup [ไม่แน่ใจ ว่าแล็บใช้ runtime ใด] · `decide()` ใช้ไมโครวินาที/ครั้ง (integration doc §4) งบเวลาโมเดลต้องไม่ทำให้ tick 4 (5 ครั้ง/วิ) ตก
- **การประกอบกัน:** `final = decide()` ; ถ้า `mode==='plan'` และไม่มี veto ที่ห้ามท่านั้น → ใช้ top-k ของโมเดลเรียงลำดับ *ขั้นย่อย* ได้ ; ถ้าท่าที่โมเดลเสนอขัด veto ใด (ตรวจด้วย `bot.brain.allowed(action)`) → ทิ้ง
- **คำเตือน:** fuzz ที่ผ่าน (≥2M ต่อเหตุการณ์, chain/chainDeep ≥8M, 0 ช่องโหว่) เป็นของ `decide()` เท่านั้น **โมเดลไม่ได้ผ่าน fuzz นั้น** — ถ้าจะใช้ ต้อง fuzz ชุด "decide + โมเดล" ใหม่ทั้งชุด

## 6. กันลอกนิสัยแย่ของรุ่นพี่

### 6.1 ป้ายผลลัพธ์ (outcome) ต่อแถว/ช่วง
| ป้าย | นิยาม (ตั้งต้น [คิดเอง] ปรับตามข้อมูล) | ใช้เป็น |
|---|---|---|
| `died` | event `death` ภายใน X วินาทีหลังแถว (X = [คิดเอง] 30) | negative label แข็ง |
| `hurt` | hp ลดเกิน Y ใน Z วินาที | negative อ่อน |
| `afk` | `idleSeconds > 30` (ตรงกับกฎ `idle` ที่มีอยู่) หรือยาวกว่า | negative — โดยเฉพาะ AFK ที่เกิดขณะ `nextStep` ยังมีงาน |
| `slow-progress` | ขั้น chain เดียวกันนานกว่าตารางวัน-ต่อ-วัน (เมื่อมี) | negative อ่อน |
| `good` | ไม่เข้าป้ายข้างบน + ก้าวหน้า chain/เก็บของ | positive |

### 6.2 กฎใช้ข้อมูล
1. **ฝึก/ปรับด้วยแถว `good` เท่านั้นสำหรับ strong label** · แถวที่เป็น `died/afk` ใช้เป็น "ตัวอย่างสิ่งที่ห้ามเหมือน" (ลบน้ำหนัก หรือใช้เป็น hard-negative สำหรับกฎใหม่)
2. **ใช้สถิติสมองเดิมจาก brief เป็นลิสต์นิสัยแย่ที่ต้องเฝ้า** (ไม่ใช่ข้อมูลฝึก): ตกที่สูงตาย · ยืน AFK · ทำบ้าน/เตียงข้างหลุม (s37) · ขุดมือเปล่า · ไม่กินตอนเลือดต่ำ · อาหารทีม = 0 (s20) · ทะเลทรายไม่มีไม้ (s22) → ทำ "bad-habit detector" ต่อข้อ แล้วนับความถี่ในข้อมูลศุกร์ → ถ้าความถี่ยังสูงเท่าเดิม แปลว่าสมองเดิมยังทำ (ยืนยันว่าข้อมูลเป็นแบบเดียวกับสถิติเก่า)
3. **veto = ข้อจำกัดแข็ง**: เช่น `dig-straight-down`, `bed-wrong-dimension`, `drop-weapon`, `self-wall-pvp`, `dont-provoke`, `piglin-container` ฯลฯ — แถวที่รุ่นพี่ฝ่าฝืน = "veto-breach" → **ตัดออกจากชุด strong label ทั้งหมด** (ไม่ว่ารอดหรือไม่) · หนึ่งหยดเดียวของท่าฝ่าฝืนไม่ให้ไหลเข้าโมเดล
4. **กฎ jing เหนือข้อมูล**: ห้ามชนะด้วยการเลิกใช้อาวุธ · บอตห้ามขังตัว/ก่อกำแพงรอบตัว · บ้านต้องพื้นราบปลอดภัย · ทองทำรองเท้าเท่านั้น (brief §1) — แถวรุ่นพี่ที่ขัดกฎเหล่านี้ถูกตัดแบบเดียวกับ veto-breach
5. **survivorship bias**: ข้อมูลมาจากบอตที่ "ยังเล่นอยู่" — ท่าที่ทำให้ตายแล้วเกิดใหม่จะมีแถวสั้น ต้องถ่วงน้ำหนักตามเวลาที่อยู่ในสถานการณ์ ไม่ใช่นับแถวดิบ
6. **ความต่างระหว่างรุ่นพี่**: ถ้า 4 ตัวทำต่างกันในสถานการณ์เดียวกัน ให้ใช้ตัวที่ outcome ดีที่สุด ไม่ใช่เสียงข้างมาก
7. **อย่าเชื่อ "ความคิด" ของสมองเดิม (qwen3:8b)** เป็นป้ายถูก/ผิด — ใช้เป็นบริบทอธิบายเท่านั้น

## 7. ตัววัดผล

### 7.1 นิยาม
| ตัววัด | สูตร | ความหมาย/ข้อควรระวัง |
|---|---|---|
| **agreement %** (ภาพรวม) | match ÷ (match+miss+extra) บนแถวที่ประเมินได้ | **ไม่ใช่เป้าให้ 100%** — ต่ำกว่าได้ถ้ารุ่นพี่ผิด ต้องดูควบคู่ "agreement บนแถว good" (`agreement_good`) และ "ความต่างบนแถว bad" |
| **agreement_good** | เหมือนข้างบน แต่เฉพาะแถว outcome ดี | ตัวที่ควรสูง |
| **disagree_on_bad** | สัดส่วนแถว outcome แย่ที่ `decide()` ทำนายท่าต่างจากรุ่นพี่ **และ** ท่าของเราถูกต้องตาม kb/วิกิ | ตัวที่แสดงว่าเรา "ดีกว่า" ได้จริง — ต้องมีผู้ตรวจแบบสุ่มแถวด้วยคน |
| **per-rule precision** | (ครั้งที่กฎยิง และรุ่นพี่ที่รอดทำท่าที่คาด) ÷ (ครั้งที่กฎยิง) | precision ต่ำ → ตรวจ threshold/ปิดกฎ (§5.a) |
| **per-rule recall** | (ครั้งที่รุ่นพี่ทำท่าป้องกัน X และกฎ R ยิง) ÷ (ครั้งที่รุ่นพี่ทำท่า X ในสถานการณ์ที่ R ควรครอบ) | recall ต่ำ → ช่องว่างความครอบคลุม/กฎใหม่ |
| **objection accuracy** | (แย้งที่ verdict=right) ÷ (แย้งที่ verdict ∈ {right,wrong}) | ไม่นับ `unknown` ในตัวส่วน แต่รายงานสัดส่วน unknown แยก (ถ้า unknown สูง ตัวเลขไม่น่าเชื่อ) |
| **objection coverage** | แย้งที่ verdict ∈ {right,wrong} ÷ แย้งทั้งหมด | วัดว่าตัดสินได้จริงกี่ % |
| **missed-error rate** | เหตุการณ์ที่รุ่นพี่เจ็บ/ตายจากสาเหตุที่เรามีกฎ แต่ผู้ฝึกงานไม่แย้ง ÷ เหตุการณ์ทั้งหมดแบบนั้น | แย้งไม่ทัน |
| **false-alarm rate** | แย้ง verdict=wrong ÷ แย้งทั้งหมดที่ตัดสินได้ | แย้งมั่ว |
| **veto-breach rate (รุ่นพี่)** | แถว veto-breach ÷ ชั่วโมงเล่น (ต่อกฎ) | ใช้เป็นตัวตั้ง baseline ว่ารุ่นพี่ฝ่าฝืนบ่อยแค่ไหน |

### 7.2 การตัดสิน verdict (right/wrong/unknown) — แนะนำให้ตัดเป็นอัตโนมัติเมื่อทำได้
- `right` = ภายในหน้าต่างหลังแย้ง (ต่อกฎ เช่น 10 วิ [คิดเอง — ที่มาของเวลาตัดสินต้องมาจาก DANGER_RULES.md เมื่อส่งแล้ว]) เกิดผลร้ายที่กฎนั้นทำนาย (เลือดลดตามที่คาด/ตาย/ตก) 
- `wrong` = ไม่เกิดผลร้ายและสถานการณ์คลี่คลายโดยไม่เกิดความเสียหาย (ผู้ท้าท้วงรายงานเกินจริง)
- `unknown` = ข้อมูลไม่พอ/หลุดการมองเห็น (ผู้ฝึกงานมองไม่เห็นรุ่นพี่)
- สุ่มตรวจโดยคน [คิดเอง] ~5–10% ของ verdict อัตโนมัติ เพื่อวัดความแม่น "ผู้ตัดสิน" เอง ก่อนเชื่อ objection accuracy

### 7.3 baseline ที่ต้องวัดก่อนเชื่อตัวเลขใด ๆ
- `decide()` กับ **ท่าสุ่ม/ท่าที่พบบ่อยสุด** (majority-class) → ได้ agreement ขั้นต่ำ · ถ้าเราชนะ baseline ไม่ขาด agreement ไม่มีความหมาย (คลาส idle/เดิน มักครองข้อมูล)
- agreement แยก "ช่วงปกติ" vs "ช่วงภัย" (มี reflex ≥50 ยิง) เพราะ 90% ของเวลาไม่มีภัย agreement รวมจะหลอก

## 9. ความเสี่ยงและสิ่งที่ยังไม่ได้ยืนยัน

- **logger ฝั่งรุ่นพี่ยังไม่มีหลักฐานว่าใส่ได้** (สมองเดิมสปาเก็ตตี้) — ถ้าไม่ได้ ตาราง §3 หลายแถวจะ "ขาด" และ pipeline เหลือครึ่งเดียว
- ค่า metadata ติดไฟ (0x01) และระยะตกจากตัวติดตาม Y ยัง **[ตรวจ] กับเซิร์ฟจริง** (MINEFLAYER_INTEGRATION §4) — ถ้าเพี้ยน กฎ `on-fire`/`falling` ใน replay จะผิดตามไปด้วย
- `team`/`flags` ต้องมีโค้ดฝั่งบอตส่งให้ (ปลั๊กอินไม่รู้เองว่าอยู่ในฐาน/ใกล้หมู่บ้าน) → ใน replay ต้อง reconstruct จาก jsonl ซึ่งอาจเดาไม่ถูก
- fuzz = จำลอง ไม่ใช่ข้อมูลโลกจริง · ไม่ได้วัดค่าหน่วงของจริง
- นับกฎ 102 vs 101 ที่รายงานก่อนหน้า (ดูหัวเอกสาร) → ตรวจว่า fuzz รอบล่าสุดครอบกฎครบหรือไม่
- ข้อเสนอที่อ้างถึง `SURVIVAL_DAYBYDAY.md`, `DANGER_RULES.md` เป็นงานอื่นใน brief — **ฉันไม่ได้อ่านไฟล์เหล่านั้น** (ยังไม่อยู่ใน repo ตอนเขียน) จึงอ้างเป็นเงื่อนไข "เมื่อมี"
- ไม่ได้ค้นเว็บ/ไม่ได้อ้างวิกี่ ในเอกสารนี้ ตัวเลขเกมที่ไม่ใช่ของแล็บจึงไม่มี
